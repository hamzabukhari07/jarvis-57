# Skill: develop

You are about to write or modify code for JARVIS. **STOP and run this checklist first.**

---

## 🛑 Step 1: Read Context First (Mandatory)
Before touching any code:
1. Read `AGENTS.md` — Project architecture, non-negotiable rules, and tool contracts.
2. Read `decisions.md` — Architectural Decision Records and established design patterns.
3. Read the relevant existing files in `actions/`, `core/`, or `memory/`.
4. Read `core/prompt.txt` if your task alters tool behavior or agent routing.

---

## 🔍 Step 2: Source Mapping for Every Output Value
Every value that will be displayed, returned to the user, or stored must have a concrete, known **SOURCE**.

*Example: Adding a new task progress reporter:*
- `task_id` ➔ Source: Generated by `core/task_manager.py`
- `progress_pct` ➔ Source: Worker progress hook (`ctx.report()`)
- `status` ➔ Source: `TaskState.status`
- `repo_path` ➔ Source: `core/repo_context.py`

> [!CAUTION]
> **If ANY value has NO defined source:**
> **STOP immediately.** Do not invent fallback values or guess. Ask the user for clarification before proceeding.

---

## 🔗 Step 3: Check the Inter-Dependency Matrix
Consult the Inter-Dependency table in `AGENTS.md`. If your change modifies a file on the left, you must inspect and update the dependent files on the right:
- Touching `actions/*.py`? ➔ Check `core/prompt.txt` & `core/action_loader.py`.
- Touching `core/task_manager.py`? ➔ Check `actions/opencode_agent.py`, `actions/kilo_agent.py`, and `actions/task_status.py`.
- Touching `memory/config_manager.py`? ➔ Check every tool calling config getters.

---

## ✏️ Step 4: Write the MINIMUM Necessary Change
- **No speculative refactoring:** Do not rewrite adjacent working code.
- **No unauthorized dependencies:** Use existing standard libraries (`pathlib`, `subprocess`, `threading`, `json`, `re`) or installed packages (`pyautogui`, `psutil`, `sounddevice`, `pycaw`).
- **Never touch `main.py` unnecessarily:** Most features belong in `actions/`, `skills/`, or `core/`.
- **Follow the `TOOL` Contract:** Every new action must export a module-level `TOOL` dict and a callable handler taking `parameters: dict` and context kwargs.

---

## 📝 Step 5: Post-Implementation Synchronization
- Update `TOOL["description"]` if parameters or tool purpose changed.
- Update `core/prompt.txt` if Gemini Live routing rules or instructions changed.
- Add an entry to `decisions.md` if a new architectural choice was made.

---

## 📢 Step 6: Standard Reporting Format
When completing your work, report strictly in this format:

```text
FILES CHANGED:
- path/to/file1.py: [Summary of changes]
- path/to/file2.py: [Summary of changes]

WHY:
[Technical rationale and architectural explanation]

WHAT TO TEST:
1. [Test Case 1]
2. [Test Case 2]
```

---

## 🛡️ Step 7: Final Step — Mandatory Verification
After completing development, ALWAYS invoke the `verify` skill (`.antigravity/skills/verify.md`).
- **Layer 1:** Static checks (compile, import, discovery)
- **Layer 2:** Runtime evidence (real file reads, live logs, actual outputs)
- **Layer 3:** Regression checks (2+ existing features)

> [!CAUTION]
> You may NOT write "FIXED" or "DONE" without completing all 3 verification layers. If runtime testing cannot be executed, mark as "UNVERIFIED" with reasons.

---

## After Development

Once code is written:

### Step 1: Verify
Invoke the verify skill (`.antigravity/skills/verify.md`).
- Layer 1: static checks
- Layer 2: runtime evidence (paste actual log/output)
- Layer 3: regression (2+ existing features)

Do NOT write "DONE" until all 3 layers pass.  
If runtime test cannot run → write UNVERIFIED with reason.

### Step 2: OpenSpec Check

If this was an OpenSpec-tracked feature:
  `openspec list`
  - If the feature is complete and verified: `/opsx:archive`
  - If not complete: leave active

If this was a plain feature (no spec): skip this step.

### Step 3: Update LEARNING_JOURNAL.md

Append an entry at the repo root:

```markdown
## [YYYY-MM-DD] — <feature name>
- What was built:
- Why this approach:
- Alternatives considered:
- Files touched:
- Lesson for next time:
```

Keep it human-readable. This is the persistent record.
