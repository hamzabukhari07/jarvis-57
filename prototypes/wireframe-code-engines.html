Four states, and what each one offers

Presence alone is not enough. The second row is the state this machine is actually in, and the state a plain "is it installed?" check would have reported as fine.

01 Not installed

Binary not found. Nothing can run.

02 Sign in required

Binary found, no account. Runs and writes nothing.

03 Ready

Installed and authenticated. Lists the models it accepts.

04 Off

The user turned it off. ZEZO will not select it, and says so if asked.

The install step

Installing runs a real program on the user's machine, so it passes the same confirmation gate ZEZO already uses for software installs: the token comes from the UI, never from the model.

Why it is built this way

01

Health, not presence

An installed / not-installed check would have shown Antigravity green during the entire failed run. The binary was there. The account was not. Any check that cannot tell those apart would have shipped a lie, which is the exact bug this section exists to prevent.

02

The reason is on the card

"Sign in required" alone is not enough for someone who does not know what a CLI is. The card says what happens if you ignore it: the engine exits in seconds and writes nothing.

03

Summary before detail

Three tallies at the top. A user opens the panel to answer one question, whether anything needs attention, and the answer should not require reading three cards.

04

Turning an engine on cannot lie

The toggle is locked off while an engine is not signed in, and the routing row states out loud that OpenCode will be used instead. A toggle that looks on while nothing runs is the same defect as a build that reports success while writing nothing.

05

Models come from the engine

The chips are read from the engine rather than typed into ZEZO's config. Today a model is passed that the CLI does not recognise and silently substitutes its own, and the settings file cannot show that.

06

Install ends with a check

A finished installer is not a working engine. After installing, ZEZO probes the engine and only then marks it ready, so an install that half-worked shows up here instead of at the next build.
