# ZEZO Skills System — Current State

> Scope: documentation only. No source files modified. Findings verified against actual code; items not executed are marked UNVERIFIED.

## 1. How it works

### 1.1 Discovery
- Skills live in `<project_root>/skills/` (`core/skill_loader.py:36`).
- `SkillRegistry.reload()` scans recursively for any file named exactly `SKILL.md` (`core/skill_loader.py:235`).
- Each skill is a folder containing `SKILL.md` with optional YAML frontmatter delimited by `---` lines (`core/skill_loader.py:39`).
- A folder whose immediate name is in `EXCLUDED_SKILL_NAMES = {"antigravity_agent", "kilo_code", "opencode", "custom_skill_10", "hamza_taste"}` is skipped (`core/skill_loader.py:114,237-238`); a parsed `name` in that set is also skipped (`:246-247`).
- If no frontmatter, the whole file becomes `instructions`, with name = folder name, description = "Skill for <name>", author = "system", version = "1.0" (`core/skill_loader.py:254-262`).
- `reload()` also creates the `skills/` directory if missing (`core/skill_loader.py:227-228`).

### 1.2 Loading / parsing
- Frontmatter parsed by a zero-dependency custom YAML parser `_parse_yaml_frontmatter()` (`core/skill_loader.py:75-111`).
- It supports: top-level `key: value`, booleans (true/yes/on, false/no/off), inline arrays `[a, b]`, block lists `- item`, empty value → `[]`.
- It does NOT support: nested maps (e.g. `metadata:` with indented `author:`/`version:`), multiline values, comments inside values, duplicate-key merge, anchors.
- Domain is taken from frontmatter `domain` or inferred by `_infer_domain_from_name_and_tags()` (`core/skill_loader.py:117-127`).
- Triggers are taken from frontmatter `triggers` or auto-generated by `_generate_default_triggers()` (`core/skill_loader.py:130-142`).
- Saved user preferences (pinned/disabled/auto_activate) are applied by skill name from `config/skills_state.json` (`core/skill_loader.py:270-274`).

### 1.3 Selection by AI
- At session build, `format_prompt_block()` (`core/skill_loader.py:374-397`) lists every non-disabled skill as `• name (DOMAIN): description` plus the instruction "Use read_skill(skill_name) before performing specialized workflows".
- Pinned skills additionally get their full `instructions` injected.
- The model decides whether to call `read_skill`; nothing forces it. Tools are directly callable.
- There is a keyword scorer `match_skills()` (`core/skill_loader.py:331-372`) and `get_active_skill_prompt()` (`core/skill_loader.py:399-424`), but **both are dead code** — `get_active_skill_prompt` has no callers anywhere in the repo (verified by ripgrep). So trigger/tag scoring never affects the live session.

### 1.4 Calling
- Three inline tools declared in `main.py:515-549`: `read_skill`, `list_skills`, `save_learned_skill`.
- `read_skill` → `main.py:1763-1766` → `SkillRegistry.read_skill()` (`core/skill_loader.py:316-329`), returns Markdown text.
- `list_skills` → `main.py:1768-1776` → `SkillRegistry.list_skills()` (`core/skill_loader.py:307-314`).
- `save_learned_skill` → `main.py:1778-1786` → `SkillRegistry.save_learned_skill()` (`core/skill_loader.py:505-569`).

### 1.5 Execution
- A SKILL.md is **declarative text only**. No code parses or executes its commands/scripts. There are no scripts in any skill package (`glob skills/**/*.{py,sh,ps1}` → no files).
- After reading a skill, the model maps the skill's steps onto existing tools itself. There is no encoded binding between a skill step and a tool.
- Fleet agents additionally receive skill bodies via `core/fleet/dispatcher.py:268-281` (prompt injection based on `agent.allowed_skills`).

## 4. Current issues

### 4.1 Bugs / broken connections
- **Dead selection code**: `match_skills()` and `get_active_skill_prompt()` have no callers; keyword scoring never runs (`core/skill_loader.py:331-424`). Verified by ripgrep.
- **Fuzzy `read_skill` can return the wrong skill**: exact match is case-sensitive; fallback is bidirectional substring and returns the first dict hit (`core/skill_loader.py:320-327`). Empty name returns the first skill instead of "not found".
- **`metadata:` nesting not parsed**: 7 skills (`git_workflow`, `make_plan`, `multi_agent_collaboration`, `office_suite`, `social_research`, `web_research_pipeline`, `web_scraper`) nest `author`/`version` under `metadata:`; the flat parser stores `metadata` as a list and never flattens, so author/version fall back to defaults (`core/skill_loader.py:75-111,249-250`).
- **`figma_helper` has no frontmatter**: parsed via fallback; its real description is ignored (`skills/figma_helper/SKILL.md:1`).
- **Hot-reload blind spot**: `get_signature()` only checks top-level entries and top-level `SKILL.md`; edits to nested `skills/<domain>/<skill>/SKILL.md` are not detected unless parent dir mtime changes (`core/skill_loader.py:178-202`).
- **Stale state entry**: `config/skills_state.json` contains only `zipped_skill`, which does not exist on disk; all 11 real skills have no state entry and use defaults. `zipped_skill` has zero runtime effect but persists until next `_save_state()` (`core/skill_loader.py:155-176,271-274`).
- **`get_skill` does not exist**: `core/fleet/dispatcher.py:274` calls `getattr(skill_reg, "get_skill", ...)` and falls back to private `_skills` dict access.
- **`save_learned_skill` always defaults domain/triggers/tags**: `main.py:1779-1785` passes only name/description/instructions + author="auto_learned", so domain is inferred and triggers auto-generated (broad/generic) (`core/skill_loader.py:505-569`).
- **`save_learned_skill` returns a tuple** from the tool handler (`main.py:1782-1786`), so the model receives a tuple repr rather than a clean string.
- **Frontend API mismatch**: backend exposes `/api/skills/install` but `frontend/src/lib/api.ts` has no `installSkill` method (from UI audit). Install control is unwired.
- **Scratch script targets wrong path**: `scratch/update_skills_tab.py` writes to `web/src/components/settings/SkillsSettingsTab.tsx`, which does not exist; real file is `frontend/src/components/settings/SkillsSettingsTab.tsx`.
- **No `remote/` directory exists**; no skill control exposure there (verified by directory listing).
- **`website_build` SKILL.md has stale paths**: claims 5 subdirectories / 23 assets; actual layout is 4 subdirectories / 20 HTML files (`skills/website_build/SKILL.md:65-95` vs actual `references/`). `core/design_resolver.py` uses the correct names, so the SKILL.md prose is the stale artifact.
- **`multi_agent_collaboration` names non-existent agents**: "Ali" and "Oscar" are not in `config/fleet_agents.json` (which has `VERVE`, `DWIGHT` etc.) (`skills/multi_agent_collaboration/SKILL.md:11,18,22`).
- **`figma_helper` references `get_active_window_info` as a peer tool**, but it is only a `computer_control` action value, not a registered tool (`skills/figma_helper/SKILL.md:15`; `actions/computer_control.py:712,768`).
- **Skills can be scanned only at install/save time**: manually dropped or post-install-edited skills bypass `scan_skill_directory`/`scan_skill_text` entirely (`core/skill_loader.py:235-291`; `core/skill_scanner.py` only called from `install_skill` and `save_learned_skill`).
- **Security scanner blind spots**: line-by-line regex only; misses `python -c`, `os.system`, `subprocess.run`, `rm -rf` variants, reordered PowerShell flags, encoded payloads across lines, unicode homoglyphs, credential reads (`core/skill_scanner.py:122-161`; `core/governance.py:142-165`).
- **Secret count is wrong**: `redacted_secrets_count` is hard-coded to 1 when any redaction occurs, regardless of how many secrets (`core/skill_scanner.py:111-116`). Executed check confirmed 3 secrets → count 1.
- **`is_safe` ignores secrets**: secret presence never sets `is_safe=False` (`core/skill_scanner.py:163`).
- **Scan runs after extraction**: files briefly exist on disk before scanning; if the scanner raises, `dest_dir` is not cleaned (`core/skill_loader.py:490-503`).
- **Extension allow-list skips many file types**: `.bat`, `.js`, `.vbs`, `.env`, extensionless files, etc. are not scanned (`core/skill_scanner.py:186`).
- **No runtime prompt-injection defense**: `format_prompt_block` and `read_skill` inject raw skill content with no scan (`core/skill_loader.py:374-397,316-329`); pinned skill bodies are injected in full with no size cap.

### 4.2 Skill bypasses (capabilities callable without reading any skill)
- All 31 auto-discovered actions in `actions/*.py` plus 9 inline tools in `main.py` are callable directly by the model. No skill read is required or enforced.
- Examples: `web_read_page` (web scraping), `web_search` (research), `file_controller` (office docs), `computer_control` (Figma/canvas), `antigravity_run`/`fleet_control` (multi-agent), `extract_design_system` + cloner (website build). Each skill merely restates tool behavior.
- Non-main AI paths (file_processor, flight_finder, gemini.py helper, code_engines, cloner, remote) have no skill access at all and bypass skills entirely.

### 4.3 Duplicated workflows
- `web_scraper`, `web_research_pipeline`, and `social_research` overlap heavily (all claim deep research/scraping/synthesis; share triggers `research`, `scrape`, `social media`, `analyze trends`, `deep search`).
- `make_plan`, `multi_agent_collaboration`, and `parallel_task_management` overlap (planning, task decomposition, agent orchestration).
- `office_suite` restates the `file_controller` tool description almost verbatim.
- `git_workflow` and `test_fastapi_deploy` both own "deploy" trigger vocabulary; `test_fastapi_deploy` is a 6-line subset of verification phases.
- `website_build` contains anti-slop gates that are also parsed directly by `core/design_resolver.py` as a runtime dependency, so the SKILL.md is both documentation and a code input.

### 4.4 Trigger collisions / dead skills
- `match_skills` uses substring `in` with no word boundaries and no minimum length; generic tags like `general` match any query containing that substring (`core/skill_loader.py:354-362`).
- Auto-generated triggers are very generic (`coding`, `deploy`, `refactor`, `research`, `scrape`, `frontend`, `component`), causing most skills to match most coding/research queries (`core/skill_loader.py:130-142`).
- `get_active_skill_prompt` is dead code, so these triggers currently have no runtime effect; but if wired, collisions would be severe.
- Skills with very narrow single-phrase triggers (`figma_helper`: only "figma helper"; `make_plan`: only "make plan"; `office_suite`: only "office suite"; `multi_agent_collaboration`: only "multi agent collaboration"; `parallel_task_management`: only "parallel task management") would rarely match natural user speech.
